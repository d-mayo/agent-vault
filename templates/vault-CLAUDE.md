# Vault guide

This vault has two sides.

- **Phone side**: everything outside `Agent/`, including `taxonomy.json`. It's my phone capture system. Read it freely; never change it. To act on a phone note, pull it in with `{{CLI}} phone pull "<path>"`; that creates an idea.
- **`Agent/`**: your workspace.
  - `Projects/<id>.md`: one overview note per project; it lists the project's GitHub repos in `repos:`.
  - `Work/<repo>/<repo>-<n>-plan.md`, `-impl.md`, `-retro.md`: one set per issue (`<n>` is the issue number or, in a Jira setup, the ticket key, e.g. `PROJ-12`; commits after a retro get a follow-up retro, `-retro-2.md`, `-retro-3.md`, ...).
  - `Ideas/<date>-<slug>.md`: one idea per file.
  - `Decisions/<project>/<project>-d<n>-<slug>.md`: one decision record per lasting decision; never edited, only replaced by a later record.
  - `Designs/<project>/<project>-design-<n>-<slug>.md`: one design per larger piece of work, a draft until sealed; a sealed design is never edited, a later design extends or replaces it.
  - `Daily/<date>.md`: the log, one file per day.
  - `Setup.md`: how this vault's stories and PRs work (tracker, merge style, approvals, repo settings, branch names, Jira specifics); written only by `{{CLI}} setup`. With no setup note the vault uses GitHub issues and works as it always has. The setup's tracker decides how issues are read and filed.
  - `.pending/<repo>-<n>.json` and `.tickets.json` (hidden, Jira setup only): in a Jira setup `{{CLI}} issue create` and `{{CLI}} idea promote` (each with its placement flag, `--standalone` for one) post nothing: each writes a pending file holding exactly the fields to post (and what the ticket is for) and prints them; the skill posts those unchanged through the connector, then `{{CLI}} issue record <repo> <KEY> --pending <file>` records the key in the ticket map `.tickets.json` and deletes the pending file. `design stories` and `features` read that map. Only `issue record` writes the map.

The scripts live outside the vault, in `~/.claude/agent-vault/`, installed from the `d-mayo/agent-vault` repo; change them there, never in place. Code repos live outside the vault. A finished project gets `status: archived` in place.

## Rules

Hooks in `~/.claude/settings.json` enforce these. If a hook blocks you, do what its message says; don't work around it.

- Create notes only with the commands below, then edit the file they create. Daily notes are written only by `log` and the pipeline commands; never edit them.
- A project reference is always `[[project-id]]` of a project that exists. If it's unclear which project something belongs to, ask me instead of guessing.
- Never write vault files through the shell (`echo >`, `sed -i`, `Set-Content`, `mv`, …): use the CLI commands below or the edit tools, which the hooks check. Sealed notes and past daily notes are never edited; if one is wrong, tell me.
- Log work with `{{CLI}} log "..." --project <id>`. Past daily notes are closed.
- A project's current truth lives in its project note (`Purpose`, `Current state`, `Architecture`, `Standing decisions`, the last generated from the decision records). Daily notes are history.

## Commands

- To record or change how this vault's stories and PRs work, say "set up this vault" (the `setup` skill); it interviews me on each value and runs `{{CLI}} setup --tracker github|jira [--merge ...] [--approvals ...] [--repo-settings ...] [--branch <pattern>] [--branch-feature <word>] [--branch-bug <word>] [--jira-... ...] [--replace]` only after I approve the exact values. The command refuses an incomplete or contradictory setup and, without `--replace`, an existing note. In a Jira setup each project with repos gets `jira_project: <KEY>`.
- `{{CLI}} new project <id> [--repo owner/name ...] [--purpose "..."]`
- `{{CLI}} new design <project> "<title>"`: the next draft design of a project (the project may not exist yet). `{{CLI}} seal design <design>`: after I approve a design; creates a decision record for each of its decisions (source `design <design> D<k>`), promotes its listed ideas, rewrites `Standing decisions` and seals it, or refuses and changes nothing. `{{CLI}} design stories <design>` lists a sealed design's feature (`feature: <owner/name>#<n> (<state>)`, or `no feature yet`) and its stories with the issues filed for them, or "not filed", marking a story that isn't under the feature. `{{CLI}} closes-feature <repo> <issue>` says whether the merge (or, for a `pr: none` story, the retro) closes the issue's finished feature. `{{CLI}} features [--project <id>]` lists the open feature issues with how many of their sub-issues are open.
- `{{CLI}} new plan <repo> <issue>`: a draft plan and an open impl note. `{{CLI}} new retro <repo> <issue>`: the retro, once the impl note has a `pr:`; once a retro is sealed and has readied a commit, the next one covers the commits made after it (`-retro-2.md`, ...). `{{CLI}} seal retro <repo> <issue>` readies an open PR (pushes the `verified:` bump, records the readied commit in the retro) and never merges; `{{CLI}} merge <repo> <issue>` then merges exactly that commit, with the merge style from `Setup.md` and, where it requires approvals, only once the PR is approved, and seals the impl note, closes a finished feature, updates the default branch and the install.
- `{{CLI}} seal plan <repo> <issue>`: after I approve a plan; records the issue's edit time and the base commit, adds the `planned` label and logs it. `{{CLI}} preflight <repo> <issue>` gates implementation; `{{CLI}} branch <repo> <issue> [--type <type>] [--slug ...]` (the type is the setup's bug word, `fix` by default, for an issue labelled `bug`, else its feature word, `feat` by default, unless `--type` says otherwise) creates and pushes the branch, named by the setup's branch pattern (default `<type>/<issue>-<slug>`); every command that takes an `<issue>` takes its number, or in a Jira setup its ticket key with the prefix of the project's `jira_project`; `{{CLI}} open-pr <repo> <issue> [--body-file <file>]` opens the PR with `Closes #<issue>`; `{{CLI}} stage <repo> <issue>` says where the issue stands. In a Jira setup `seal plan`, `preflight`, `branch`, `open-pr`, `seal retro` and `stage` take `--ticket <file>`: the ticket as JSON (`key`, `title`, `body`, `type`, `labels`, `parent`) that the skill fetched through the connector and wrote outside the clone and the vault, so the CLI never reads the issue from GitHub; `{{CLI}} tracker <repo>` prints the tracker and, for Jira, the connector, the project key, the ticket file's fields and the issue types. Nothing ever changes a ticket's status. `branch` and `open-pr` run inside a clone of the repo.
- To file an issue, say "file an issue for ..." or "turn this idea into an issue" (the `issue` skill); it drafts the title and body in the issue template, asks about anything unclear, and creates it through `{{CLI}} issue create` with a placement flag (`--parent`, `--standalone` or `--bug`) only after I approve the exact wording and placement. Never `gh issue create`: a hook blocks it in registered repos. The same hook blocks removing a feature's `feature` label or a sub-issue link (`gh issue edit --remove-parent`, `--remove-sub-issue`, `--remove-label feature`, `gh label delete feature`, the matching `gh api` calls): I change those by hand on GitHub.
- To design something larger than one issue (a new project, a feature, a refactor, or several ideas combined), start a fresh session on Opus (by convention) and say "design ..." (the `design` skill); it researches first, interviews me over as many rounds as it needs, gets an independent Opus review, seals the design only once I approve the summary, then drafts one issue per story for me to approve. Ask it later to "file the stories of <design>" for any left unfiled.
- To plan an issue, start a fresh session on Opus (by convention) inside the repo clone and say "plan #<issue>" (the `plan-story` skill); it researches first, interviews me only on what research can't settle, gets an independent Opus review of the draft, and seals only once I approve the summary.
- To merge a readied PR, say "merge #<issue>" (the `merge` skill); on its own it asks me to approve a summary, and right after an approved retro it asks nothing more. A PR whose retro was approved needs no second approval, and one that changed since needs a follow-up retro first (and, where `Setup.md` requires approvals, new approvals).
- To hand stories over entirely (plan, implement, review, retro and merge with no approvals from me), start a fresh session on Opus (by convention) inside the repo clone and say "handoff #<issue>" (or several issues, or a feature) (the `handoff` skill); it asks me only when it isn't sure, and runs the implementation on a Sonnet subagent. Where `Setup.md` requires approvals it stops when the PR is ready, and I collect them and say "merge #<issue>"; rerun it afterwards to go on with the next story.
- To implement a sealed plan, start a fresh session inside the repo clone and say "implement #<issue>" (the `implement-story` skill); it stays on this session's model (Sonnet, by convention) and runs its own review on Opus.
- `{{CLI}} repo-init <path>`: one-time setup of a repo clone, following the vault setup: the setup's merge style (set, allowing only that style, where repo settings are managed; only checked otherwise), shared pre-push hook, `CLAUDE.md` skeleton, and, in a GitHub setup only, the `planned`, `feature` and `bug` labels and `.github/ISSUE_TEMPLATE/issue.md`; the skeleton and template are left uncommitted.
- `{{CLI}} idea add "<title>" [--project <id>] [--source ...]` and `{{CLI}} idea drop <file> --reason "..."`, `{{CLI}} idea promote <file> --body-file <file> [--title "..."] [--repo <name>] (--parent <n>|<repo>#<n> | --standalone | --bug)` (creates the GitHub issue from a body in the issue template; only after I approve)
- `{{CLI}} issue create <repo> --title "..." --body-file <file> [--idea <file>] (--feature <design> | --parent <n>|<repo>#<n> | --standalone | --bug)`: the one way to create a GitHub issue, and exactly one placement flag is required; `--feature <design>` files the sealed design's feature issue (label `feature`) and attaches its filed stories as sub-issues, `--parent` files the issue under an open feature, `--standalone` files it under none with no label, `--bug` files a standalone issue labelled `bug`; refuses a body that isn't the issue template (`{{CLI}} schema` lists its sections), and only after I approve the exact title and body
- `{{CLI}} decision add <project> "<title>" --decision "..." --why "..." --source "plan <repo>#<n> D<k> | design <design> D<k> | issue <repo>#<n> | retro <repo>#<n> | session" [--replaces <record>]`: with `{{CLI}} seal design <design>`, the only way to write a decision record; it also rewrites the project note's `Standing decisions` (generated, never hand-edited). `{{CLI}} decisions [--project <id>] [--all]` lists the active records (`--all`: superseded too).
- `{{CLI}} ideas [--project <id>] [--status open]` lists ideas; `{{CLI}} ideas review [--older-than <days>] [--project <id>]` lists open ideas older than that many days (default 90), grouped by project (`(no project)` for none), oldest first.
- `{{CLI}} phone list` and `{{CLI}} phone pull "<path>" [--project <id>]`
- `{{CLI}} log "<text>" [--project <id>]`
- `{{CLI}} restore <note> [--snapshot <id>] [--list]`: puts a note under `Agent/` back byte for byte from the history of `Agent/` (a snapshot taken at the first session start of every vault or repo session, kept outside the vault); `--list` shows the snapshots where the note changed. The Stop hook names this command when a sealed note changed through the shell: tell me, and only run it if I ask.

`{{CLI}} lint` (run inside a clone) runs `claudemd-lint` and then the repo's declared `Lint:` command; it fails rather than skip a missing tool. `{{CLI}} schema` prints the full note rules. `{{CLI}} status` lists projects and the open idea count. `{{CLI}} validate` checks everything.
