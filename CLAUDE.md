# agent-vault

## Purpose
Scripts, hooks and skills for the Claude + Obsidian workflow; installed to `~/.claude/` by `install.py`.
Project: agent-vault. Design record: `docs/design-v1.md` (sealed; the code is the source of truth).

## Commands
<!-- covers: install.py, tests/**; verified: 2026-11-16 -->
- Run tests: `python -m unittest discover -s tests -t .` (stdlib only, but the tests need `ruff` on your PATH; pytest also works). It runs the test classes in parallel worker processes (`tests/parallel.py`); setting AGENT_VAULT_TESTS_SERIAL to 1 runs it all in one process, and AGENT_VAULT_TESTS_WORKERS to a number sets the worker count (default: the CPU count, at most the number of classes)
- Lint: `ruff check .`
- Reviewer evals: after changing a reviewer file (the ones `evals/score.py` maps), run them in a session in this clone: "run the reviewer evals for <reviewer>" (the reviewer-evals skill). `python evals/score.py --status` shows which reviewer files changed since their baseline.
- Install locally: `python install.py --vault <path to Notes>`
- CLI after install: `~/.claude/agent-vault/bin/vault <command>`, a POSIX sh launcher that install.py writes, which runs the recorded Python on the installed vault.py; the exact string (which the vault's permission rule matches) is lib.CLI, the same on every machine, and is written into the vault's CLAUDE.md. It runs in Bash only; in PowerShell or cmd use the recorded Python and vault.py (the installer prints that line).

## Layout
<!-- covers: agent_vault/**, install.py, templates/**, skills/**, agent_vault/githooks/**, .github/**, evals/**, .claude/skills/**; verified: 2026-11-16 -->
- `agent_vault/`: everything copied to `~/.claude/agent-vault/`. `agent_vault/bin/vault` is the CLI launcher (d59): a POSIX `sh` script, LF and executable, that runs the config's `python` on `agent_vault/vault.py` as installed; `lib.CLI` names it. `agent_vault/lib.py` holds the schema and shared helpers, the one atomic write path into the vault (`write_text`/`write_bytes`: a hidden temp file renamed over the target) and the history of the vault's Agent folder (`snapshot`: a git repository at `agent-vault-history.git` beside the config, never in the vault, which SessionStart fills and `vault.py restore <note> [--snapshot <id>] [--list]` reads; the Stop hook names the restore command for a note changed through the shell) and the setup note (Agent/Setup.md, frontmatter only: how the vault's stories and PRs work; written only by `vault.py setup`, checked by `setup_problems` for both that command and `validate`, and read only through `read_setup`, which returns the defaults (GitHub, squash, no approvals, managed repo settings, branches {type}/{issue}-{slug}) when there is no note; not fingerprinted by the Stop hook); `agent_vault/vault.py` is the CLI (`seal retro` readies an open PR and records its commit in the retro, and `merge` merges that commit and seals the impl note; in a Jira setup `issue create` and `idea promote` (each with a placement flag: `--feature`, `--parent`, `--standalone` or `--bug`) post nothing but write `Agent/.pending/<repo>-<n>.json` with the fields to post, which a skill posts through the connector before `issue record <repo> <KEY> --pending <file>` records the key in the ticket map (.tickets.json beside it), the one file `design stories` and `features` read there); `agent_vault/github.py` is the only place that runs `gh` and `git` (`AGENT_VAULT_GH` overrides where `gh` is found); `agent_vault/claudemd.py` lints `CLAUDE.md` (paths, commands, covers globs, size cap, the `Lint:` line and staleness; `vault.py claudemd-lint` runs it; `vault.py lint` runs it and then the repo's declared `Lint:` command); `agent_vault/hooks/` holds the Claude Code hooks.
- `agent_vault/hooks/push_guard.py`: user-level guard for the Bash and PowerShell tools (no pushes to main, no `--no-verify`, no `gh issue create` or `gh issue new` aimed at a registered repo: issues go through `vault.py issue create` with a placement flag (`--feature`, `--parent`, `--standalone` or `--bug`); and in a registered repo nothing that removes a feature's `feature` label or a sub-issue link: the user does that by hand on GitHub).
- `install.py`: idempotent installer; replaces the installed code and skills file by file from a staged copy under `~/.claude/agent-vault.staging/` (never delete-then-copy, so a running hook never finds its script missing); owns only settings entries whose command contains `/.claude/agent-vault/`; writes the vault path, its own Python (`python`), the CLI permission, the clone it came from (`source`) and the installed commit (`commit`, `commit_time`; the hidden `--commit` sets it when installing from an export) to `~/.claude/agent-vault.json`; `install.py --uninstall` removes all of that (and this clone's `core.hooksPath`) but never the vault's notes or `CLAUDE.md`.
- `templates/vault-CLAUDE.md`: the vault's `CLAUDE.md`, with `{{CLI}}` filled in at install.
- `agent_vault/templates/repo-CLAUDE.md`: the skeleton `repo-init` writes for a newly registered repo's own `CLAUDE.md`.
- `skills/`: user-level skills; each subfolder is copied to `~/.claude/skills/`. Every pipeline skill carries the same `## Approvals, pings and the closing summary` section (three-option approval prompts, one push notification when a stage hands off, a closing summary of at most three bullets), kept identical by a test.
- `skills/implement-story/`: takes a sealed plan from branch to open PR, step by step, with one review at the end (re-reviews cover only the fixes, at most two reviews; a repo's `Known test failures:` Gotchas line lists failures that don't block) (a plan with `pr: none`, which `seal plan` allows only if every step's `Files:` is `none`, has no branch, PR or review: its steps are recorded as `Step <n>: done` lines in the impl note); a request that says "Steps only" runs just Start and the steps, returns a report and leaves the review and PR to the caller (handoff's implementer); `skills/implement-story/reviewer.md` holds the reviewer's own prompt and findings format.
- `skills/plan-story/`: turns an issue into a sealed plan, researching first, interviewing only where research leaves something ambiguous, and reviewing the draft with an independent reviewer before the user approves it; `skills/plan-story/plan-reviewer.md` holds the reviewer's own prompt and findings format.
- `skills/design/`: turns a larger idea into a sealed design note, decision records and one issue per story: researches, interviews over as many rounds as needed, holds the draft to the rigor rules, has an independent Opus reviewer check it (`skills/design/design-reviewer.md`), seals with `vault.py seal design` once the user approves, then files the design's feature (`vault.py issue create --feature`) and its stories under it (`--parent`); `vault.py design stories` shows the feature and which stories are unfiled, and `vault.py features` lists the open features.
- `skills/issue/`: the one way to create a GitHub issue: drafts the title and body in the issue template (`lib.ISSUE_SECTIONS`), asks about what's unclear, and places the issue (under a feature, `--standalone` or `--bug`) and calls `vault.py issue create` only after the user approves the exact wording; the retro and plan-story skills call that command too.
- `skills/retro/`: closes out an issue before merge — audits the repo `CLAUDE.md`, its `README.md` and the project overview one heading at a time, sorts follow-ups, including every `→ left open` review finding (named by a trailing `(R<n>)`; `seal retro` refuses an unsorted one), into an issue, an idea or dropped, and seals (`seal retro` also refuses an open issue whose PR no longer closes it; for an open PR it pushes the `verified:` bump, writes the readied `commit:` into the retro, seals only the retro, leaves the impl note open and never merges, printing the next step for the setup's approvals; for a `pr: none` plan it instead closes the issue itself with the retro's `## Closing comment`, commits nothing and needs no branch, and a closed issue or a PR already merged or closed seals both notes); commits after a sealed retro get a follow-up retro (`new retro` makes `<repo>-<issue>-retro-<n>.md`, covering only those commits); also runs as a backfill for an issue that already merged without one. A finished feature is closed by the merge (by `seal retro` for a `pr: none` or backfilled issue; a failure there only warns); `vault.py closes-feature <repo> <issue>` runs the same read-only check, so the retro summary can name the feature.
- `skills/merge/`: merges a story's PR once its retro has readied it: runs `vault.py merge <repo> <issue>`, which merges only the commit the latest retro readied, with the setup's merge style, and refuses unless the PR is open at that commit, the clone is on it, every check passed (none still pending, and none "not started" in a repo with Actions workflows), the PR is `APPROVED` where the setup requires approvals and the repo allows the style; then it seals the impl note, closes a finished feature, brings the default branch up to date and self-updates (a rerun on an already merged PR does only those steps). When the PR head moved it runs a follow-up retro and, where approvals are required, stops for new approvals; on its own it asks the approval prompt for a summary, straight after an approved retro it asks nothing more; it never updates the PR branch itself. A pipeline skill, with the shared approvals section.
- `skills/handoff/`: an orchestrator for stories the user hands over entirely (one issue, several, or a feature), run in one top-level Opus session: plans each story itself (plan-story's procedure, sealing without asking), has a Sonnet subagent implement the steps (implement-story's `## Steps only` route), runs the Opus review, writes the retro (which readies the PR) and merges through `vault.py merge`, one story at a time, asking only when unsure; where the setup requires approvals it stops when its current story is ready and merges nothing; it never creates or edits an issue (in a Jira setup, a ticket: it fetches each through the connector, expands a feature from the ticket map and skips a story `stage` reports done). It is not a pipeline skill: it doesn't carry the shared approvals section, and the section's identity test covers the six pipeline skills (`PIPELINE_SKILLS` in `tests/test_skills.py`).
- Jira setup (design 4): `seal plan`, `preflight`, `branch`, `open-pr`, `seal retro` and `stage` take `--ticket <file>` (a JSON ticket file with `key`, `title`, `body`, `type`, `labels` and `parent`, read and checked by `lib.read_ticket`, written by the skill outside the clone and the vault) and never read the issue from GitHub; a sealed Jira plan has `ticket_hash` instead of `issue_updated`; `vault.py tracker <repo>` tells a skill the connector, project key and ticket fields; a story's work is merged when a PR carrying its key has (`github.merged_prs`); plan-story, implement-story, retro, merge and handoff each have a `## Jira setup` section; `stage` takes `--ticket` optionally in a Jira setup and then answers from the notes, the ticket map and GitHub's PRs alone (`stage_of`, the same done judgement as `design stories`, `jira_story_done`), which is also SessionStart's stage line there, never calling Jira; handoff's Jira path expands a feature from the ticket map through `design stories` (which names each story's repo) and skips a story `stage` reports done.
- `skills/setup/`: interviews the user on the vault's setup (tracker, merge style, approvals, repo settings, branch pattern and type words, and for Jira the connector, issue types, planned label and project keys), shows the exact values (and, with a note present, what changes) and runs `vault.py setup` only on an explicit yes. Not a pipeline skill: no shared approvals section, no ping.
- Decision records (`Agent/Decisions/<project>/`): one per lasting decision, created only by `vault.py decision add` or, for a design's decisions, `vault.py seal design`, never edited and replaced by a later record (`--replaces`). The guard blocks the edit tools on them and the Stop hook fingerprints all but `status` and `superseded_by`. A plan decision line ending ` (lasting)` needs a record before `seal retro`; the overview's `## Standing decisions` is generated from the records.
- Designs (`Agent/Designs/<project>/`): a draft until `vault.py seal design` records its decisions, promotes its ideas and seals it; a sealed design is never edited (a later one `extends` or `replaces` it). The guard blocks the edit tools on a sealed one and the Stop hook fingerprints it; `vault.py design stories` shows which stories have no issue yet.
- `agent_vault/selfupdate.py`: keeps the install current without a manual `install.py`: when the config's `source` clone has a `main` newer (committer time, local refs only) than the installed `commit_time`, it exports `main` with `git archive` and runs that copy's `install.py`, under a lock file; the SessionStart hook calls it first in every session and `vault.py merge` calls it after a merge in the source clone (or a worktree of it); it returns one line to print, never raises, and does nothing for a config without `source`.
- `agent_vault/githooks/pre-push`: blocks pushes to `main` and branch names that don't follow the setup's branch pattern (it asks `vault.py check-branch`), and runs `vault.py lint` on any push that creates or updates a branch. The one copy: this repo's `core.hooksPath` points at it, and `repo-init` points other repos at the installed `~/.claude/agent-vault/githooks/`.
- `.github/workflows/test.yml`: the CI (d61): `ruff check .` and the unit tests on Windows and macOS with Python 3.9 and 3.12, on every pull request and push to `main`; not a required check, but `vault.py merge` waits for its jobs.
- `.github/ISSUE_TEMPLATE/issue.md`: the GitHub issue template for this repo, identical to what `repo-init` writes (generated from `lib.ISSUE_SECTIONS`; a test keeps them equal).
- `evals/`: eval cases for the three reviewer prompts (`evals/<reviewer>/<case>/` holds that reviewer's material files and an expect.json of planted defects), the scorer `evals/score.py` (scores reviewer replies saved under evals/out/, which is git-ignored, beside `evals/baseline.json`; `--status` lists the reviewer files changed since their baseline entry), never part of the full check beyond `tests/test_evals.py` and never installed; `evals/prompt.py` builds the full prompt for one review of a case (`<reviewer> <case> --out <file>`).
- `.claude/skills/reviewer-evals/`: this repo's own project skill (never installed): runs the reviewer evals for one reviewer, launching the reviewer on Opus three times per case from the prompt `evals/prompt.py` builds, saving the replies under evals/out/ and showing the scores against the baseline.
- `tests/`: unittest suites; hooks and the CLI are run as subprocesses with `AGENT_VAULT_CONFIG`. `tests/fake_gh.py` stands in for `gh` (`AGENT_VAULT_GH`); tests never touch GitHub. `tests/helpers.py`'s `restore_or_build` and `tests/test_github.py`'s `snapshot` build a repeated setup once per process and copy it per test.

## Conventions
<!-- covers: agent_vault/**; verified: 2026-11-16 -->
- Standard library only; Python 3.9+; must run on Windows and macOS.
- Scripts find the vault through `~/.claude/agent-vault.json` (`lib.VAULT`); `AGENT_VAULT_CONFIG` overrides it. With no config, the CLI exits with an error (except `lint`, which reads nothing from the vault) and Claude hooks exit 0 silently.
- Hooks never write `__pycache__` (`sys.dont_write_bytecode`), never block a session from starting, and report blocks with exit code 2 and a message on stderr.
- All note rules live as constants in `agent_vault/lib.py`; `vault.py schema` prints them from there.

## Gotchas
<!-- covers: agent_vault/hooks/**, install.py; verified: 2026-11-16 -->
- Hook commands are absolute forward-slash paths to the installer's Python (`sys.executable`) and the script, so they don't depend on PATH or how the Windows hook runner expands `$HOME`. `lib.CLI` is the constant launcher string `~/.claude/agent-vault/bin/vault`, never built from `sys.executable`; the vault's `Bash(~/.claude/agent-vault/bin/vault:*)` permission must match it exactly. The launcher needs the executable bit (git mode 100755, `.gitattributes` pins LF) and a `~/` command in this file is only a warning when the file is missing.
- `.gitattributes` pins LF endings: a CRLF `agent_vault/githooks/pre-push` fails in bash and blocks every push.
- `agent_vault/hooks/push_guard.py` tokenizes quote-aware and treats heredoc bodies as data; add a test case for every new command shape it must handle. Its `gh issue create` rule reads the vault config, so those tests must pass a temp config (`AGENT_VAULT_CONFIG`) or they read the real machine's.
- The history lives in the config's folder (`lib.history_dir()`, read from `lib.CONFIG` at call time), so a test or fixture must keep its config in its own temp folder or the snapshot lands in the real `~/.claude/`; an in-process test patches `lib.CONFIG` and `lib.VAULT` first. A snapshot is time-boxed to 5 seconds and fails silently, so a hook that depends on one must read the id from the session state, which may be `None`.
- The pre-push hook is one shared file, so it takes Python from the `python` field of the config (never `PATH`) and runs the vault CLI script next to its own folder (for `check-branch` and `lint`); with either missing it refuses the push and says to rerun `install.py`.
- Remote tools can't write `~/.claude/` folders; only `install.py`, run on the PC, can (by hand, or through `selfupdate`). An install from before `source` existed needs one manual run.
- A test that lets `selfupdate` install must put its config at `<tmp>/.claude/agent-vault.json` (it installs only when the config sits in a `.claude` folder, so a test never touches the real `~/.claude/`) and use a fake `install.py`; an install from the `git archive` copy has no git `HEAD`, so compare the config's `commit`, not `HEAD`.
- CI runs the tests on Windows and macOS with Python 3.9 too: compare a recorded or printed path to a temp path with `os.path.samefile` (CI temp paths come as `RUNNER~1` short names on Windows and through `/var` → `/private/var` on macOS), run bash through `find_bash()` in `tests/helpers.py` (the Windows runner's first `bash` is WSL's), and avoid 3.10+ APIs (`tests/__init__.py` lets `Path.write_text` take `newline=` below 3.10, for tests only).
- Test classes run at the same time, so a test must not share any path or state outside its own temp folder (no fixed temp names, no writes under the repo or `~`); a repeated setup is copied per test, never shared.
